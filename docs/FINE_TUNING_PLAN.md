# Fine-tuning plan: teaching a Qwen model our IR

Status: stopped after S1 by the stop rule (2026-10-26): the tuned 0.8B did not beat the prompted 4B on M1. S1 on the 4B with QLoRA (2026-10-27) won the grounded set but not M1, so it also stays a comparison model (D-025). Next: S2, broader data outside the generator families (planned below, not started). Results: `docs/agents/training.md`. The original plan follows.

## Why fine-tune

On IR v2 the remaining challenge failures are model behaviour, not missing IR: revolving a centred circle for a boss, patterning a feature before it exists, placing a port outside the face after being told the valid range, putting a selector word into a numeric field, and ignoring precise repair messages. Prompt work has stopped paying off (planning step and staged emission both lost their A/B, D-013 and D-019). Fine-tuning on verified IR is the documented route for this gap: CAD-Coder cut non-executable CAD code from 98.8 % (base Qwen2.5-7B) to 1.45 % with SFT and RL (`docs/research/ir-completeness.md`).

## Success criteria

| Gate | Target | Today (qwen3.5:4b, prompted) |
|---|---|---|
| Challenge set (held out, never trained on) | 2/2: one valid solid, every check, all 16 named parameters, +5 % robustness rebuilds | 0/2 |
| M1 set | ≥ 6/10 fully correct and ≥ 24/35 checks (the best v1 run) | 4/10, 16/35 |
| Grounded set, grounded mode | ≥ 3/10 and ≥ 23/45 checks | 3/10, 23/45 |
| Synthetic held-out set | ≥ 90 % schema-valid, ≥ 80 % build, ≥ 70 % all checks | not measured |

## Data: the real work

All samples are generated by us, built by our geometry service and kept only if they pass, so every label is verified. Nothing from the eval sets enters training.

1. **Procedural design generators** (`training/generators/`), one per family, sampling parameters and emitting IR v2 directly:
   prismatic blocks and manifolds with ports on several faces, crossing passages, tapped and counterbored holes; plates and brackets; L/U/T profiles; flanges and bolt circles; enclosures and trays with shells; turned parts (bushings, spacers, grooves); parts with bosses, ears, ribs and pockets via face references, paths and patterns. Each design is built, validated and DFM-checked; rejects are discarded. Ground-truth checks (extents, hole counts and diameters, spacings, counterbores, crossings, axes, named parameters) are derived from the generator, not from the model.
2. **Prompt renderers**: several phrasings of the same design — a one-line request, a bullet spec, a numbered REQ list, and long markdown specs with sections (overall dimensions, external geometry, ports per face, mounting, required parameter names, manufacturing constraints) in the style of the challenge prompts but never their text. Optional paraphrase by the local 4B, kept only if every number survives (the grounding check we already use).
3. **Repair pairs**: valid designs mutated with the failure modes seen in the replays (revolve for a boss, missing plane, pattern before its source, port outside its face, overlapping holes, wrong field types, overlong answers). Running our validator and kernel on each mutant gives the real error text; the sample teaches "broken design + these problems → corrected design", which is exactly where the 4B fails today.
4. **Refine pairs**: a design plus a change request ("make the block 10 % longer", "add a second port on the left face") → parameter updates or a new design.
5. **On-policy successes**: run the current agent on generated prompts and keep verified successes, so the training distribution includes the model's own style.
6. **Leakage guard**: the challenge, M1 and grounded prompts are excluded, and any generated prompt with high n-gram overlap with them is dropped.

Mix about 60 % generate, 25 % repair, 15 % refine; 2k samples for the toy run, 15–25k for the real run.

## Format

Training uses the same chat format as inference, but with the short v2 rules only and no worked examples: the examples cost about 4k tokens per call, and a fine-tuned model should not need them. That brings a challenge-sized sample (spec ~2k tokens, design ~3k) to about 5–6k tokens. Loss on assistant tokens only. JSON targets are produced by `Design.model_dump_json` so the model learns one canonical form.

## S1 within 6 GB

S0b result (see `docs/agents/training.md`): 39/40 on held-out synthetic cases but 0/10 on M1 against 4/10 for the prompted 4B. S1 is therefore about transfer, not more of the same templates, and it has a stop rule: **if S1 does not beat the prompted 4B on M1 and the grounded set, the 0.8B route stops** and the effort goes back into the prompted 4B. Training the 4B itself needs more than 6 GB (D-021).

0. **Real-wording data first.** The biggest lever is paraphrase: every templated prompt is rewritten by the local `qwen3.5:4b` in several registers (terse, chatty, spec sheet, mixed units and number words). A paraphrase is kept only if every number survives. Add vague prompts with defaults ("a metal bracket with screw holes"), and part names used loosely: a "bracket" that is a flat plate, a "flange" that is a round plate. Track M1 and grounded scores per S1 checkpoint, not the training loss.

Everything stays on the laptop. Figures measured in S0 (`docs/agents/training.md`): bf16 LoRA r16 on Qwen3.5-0.8B peaks at 4.4 GB with 4,096-token sequences and batch 2, and trains at about 1,100 tokens/s. That speed uses the slow fallbacks: no `causal_conv1d`, no flash-linear-attention, and PyTorch attention because the installed xformers was built for another torch.

1. **Fix the kernels before scaling.** Add `flash-linear-attention` (Triton, no compile) and `causal-conv1d` (needs the CUDA toolkit in WSL, about 3 GB, or a matching wheel), and remove the mismatched xformers. Re-run the S0 data as a benchmark: the same 247 steps, now 47 min. Expect 2–3x (estimate). Without it, S1 is 6–8 h per epoch.
2. **Model: stay on 0.8B.** Qwen3.5-2B needs 5 GB at short sequences, and our samples run to 4k tokens (6k for spec-sheet-length prompts). Try it only as a 20-step memory probe (batch 1, 4,096 tokens) after step 1. That costs a 4 GB download at about 1.3 MB/s, so about 50 min.
3. **Sequence budget.** S0 maxed at 3,728 tokens. S1 adds challenge-length specs (about 2k-token prompt plus 3–4k-token design). Use `max_length` 6,144 at batch 1 with 8 accumulation steps; memory falls with batch 1, so measure it on the first steps. Drop anything longer instead of truncating it, because a cut-off design teaches cut-off answers.
4. **Data, about 15k samples, about 25M tokens.**
   - A complex manifold family built from the challenge's feature vocabulary, never its text: terraces, several bosses with bores, ears from a path plus a pattern, rib patterns on the side walls, a recessed front panel with filleted corners, a bottom chamfer, and ports on four faces with crossings.
   - Enclosures with shells, flanges sized from standard tables, and angled holes from datums.
   - Refine pairs.
   - At least a quarter long spec-sheet prompts.
   - Paraphrases by the local `qwen3.5:4b`, kept only when every number survives. S0 reached a loss of 0.002, so the model memorises our templates. Phrasing variety is what moves the real-text gates.
   - On-policy successes from the local 4B agent.
5. **Schedule.** One epoch overnight first (about 3 h with the kernels, about 6 h without). Run a second epoch only if the M1 and grounded scores, not the synthetic one, are still improving.
6. **Export.** Merge, convert with llama.cpp (`convert_hf_to_gguf.py --outtype q8_0`, pinned release), then `ollama create` with the base model's renderer, parser and sampling parameters (`training/wsl/Modelfile`). Ollama cannot import Qwen3.5 safetensors on Windows (it needs its MLX runtime).
7. **Gates.** The success criteria above, on the same commands: synthetic held-out, M1, grounded and challenge, all measured against `qwen3.5:0.8b-q8_0` and `qwen3.5:4b` as they are prompted today.

## S2: breadth outside the generator families (planned 2026-10-27, not started)

S1 on the 4B (D-025) won the grounded set but lost M1 by one case. The failures, and what they say about the S1 data (`data/training/s1/train.jsonl`, 4,250 designs):

| Seen in the runs | Cause in the data |
|---|---|
| 8.5 mm holes became M5, 18 mm became 17.5, 6.6 mm became M4 (`dp2`, `dp3`, `g09`) | 78 % of holes name an M-size, and prompts never state a plain diameter for a fastener hole |
| "31 mm square" read as an edge margin, giving a negative spacing (`nema17`); "spaced 85 x 60" gave no holes at the right pitch (`dp2`) | every grid is placed by `hole_margin` or `mount_margin`, never by the stated spacing |
| T-plate and ten-hole plate holes outside the part (`dp6`, `in2`) | every outline is centred on the origin; no polygon, path or slot outlines with holes placed relative to them |
| the L-bracket's outer-corner fillet fails the kernel every time (`dp21`) | bent parts never ask for fillets on chosen edges |
| the same broken answer on all four attempts (4 of the 5 never-built M1 cases) | repair samples only fix our own mutations, so real kernel errors are out of distribution |
| prompt quotes that are not in the prompt ("135 mm wide") | quotes are copied from template phrases; nothing checks that a quote appears in the request |
| a kept 6 mm thickness came back as 10 (`g09`) | edit samples rarely keep explicit diameters and thicknesses |
| — | 50 titles and 57 parameter names; slot, path, datums, `through_all`, `two_sided`, `taper` and mirror patterns never appear |

Data changes, about 5k samples so the 4B run stays one night (608 steps, 8 h):

1. **Holes by what the request says.**
   - Mix: stated diameters about 50 % ("8.5 mm holes", "Ø6.6", "6.6 dia"), M-sizes about 30 %, both about 20 % ("M8 clearance, 9 mm").
   - The target keeps `diameter` whenever the request gives one, and the hole check uses the stated value.
2. **Placement by what the request says.** The phrasing of each pattern is drawn independently of the geometry, and the parameters are named after that phrasing (`hole_spacing_x`, not `hole_margin`):
   - centre spacing ("spaced 85 x 60", "on a 47 mm square")
   - a bolt circle or PCD
   - margin from the edges
   - coordinates from a corner or edge
   - rows times columns at a pitch
   - slot centres
3. **New outlines and families.**
   - Outlines: T, L, U, cross and gusset plates from polygons and paths, not centred on the origin; slotted plates; standoffs and spacers.
   - Bent parts: L, U and Z brackets with holes on each leg's own face, and fillets or chamfers on named edges.
   - Clamp blocks, shaft collars and keyed hubs (cut extrudes).
   - Every IR entity, placement and extent used at least once in 2 % of designs.
4. **Standard-referenced parts** from a small public table (`standards.py`, like `fasteners.py`, each row citing its source): EN 1092-1 PN10/PN16 flanges, NEMA motor faces, aluminium-extrusion slot pitches and 6000-series bearings. The sizes the eval sets use are left out of training (DN50, NEMA 17, NEMA 23, 2020), so the model learns to use the table rather than memorise eval answers.
5. **Names decoupled from shapes.** About 300 titles and an open parameter vocabulary: synonyms, and names taken from the request's own words. The same name is used for different shapes ("bracket" can be a plate, an L or a gusseted angle).
6. **On-policy repairs.**
   - Run the prompted `qwen3.5:4b` and `partwright-ir:4b-s1` on about 600 new generated prompts (about 4 h at night), and keep each failing answer with the agent's real error text, paired with the verified design.
   - Add kernel-error repairs that the mutator cannot produce: fillets too large, holes outside the part, overlapping holes.
   - About a quarter of the repair samples come from this source.
7. **Honest provenance.** Every training quote must appear verbatim in the request, and samples that fail are dropped.
8. **Edits that keep values.** Prior-design requests that change one thing must keep every explicit diameter, thickness and spacing exactly.

The S1 data is reused, re-rendered for items 1, 2 and 5 rather than added as-is. Rough mix: 35 % new families and outlines, 25 % re-rendered S1, 20 % repairs, 10 % edits, 5 % standards, 5 % requirement extraction.

Before any training (cheap checks):
- coverage counts for items 1–5 on the data card;
- the 8-gram leak guard against M1, challenge, grounded and the dev set below;
- every design built and checked under the default rules, as now.

Gates and stop rule, unchanged in substance: the tuned 4B must beat the prompted 4B on M1 and on the grounded set.

Agent fixes found on the way. These are not data work; they get their own changes and are measured before S2 so the baseline moves first:
- the loop should notice an identical repeated answer and re-sample;
- the validator should flag a prompt quote that is not in the request.

Open questions for the user:
1. **Repeated gate runs.** M1 is 10 cases sampled once, and S1-4B lost by one case. Should each gate be run three times and the means compared?
2. **A dev set.** Should we write a 20-case hand-written dev set (`evals/cases/dev.yaml`, new parts, never trained on) to pick the best of the 100-step checkpoints, keeping M1 and grounded as the gates only?

Rough cost: generator and pipeline code over a few sessions, one night of on-policy collection, one night of training, about an hour for export and gates.

## Risks

- **0.8B may lack the capacity** for 7k-character specs; S0/S1 measure that cheaply before any spend.
- **Synthetic-to-real gap**: generated specs are cleaner than real ones; the grounded set and the challenge prompts (real text) are the guard.
- **Long samples on 6 GB**: 5–6k-token sequences are above the 2k figure Unsloth quotes for 0.8B at 3 GB; expect to cap sample length or move S1 to the rented GPU as well.
- **Disk**: the WSL training environment needs 6–8 GB on C:, which has about 7 GB free; D: has about 12 GB.
- **Chat template / EOS mismatch** after GGUF export silently degrades output; the S0 gate catches it.

## Decisions

1. Cloud GPU: no. Training stays local (2026-10-26), so the 4B is not fine-tuned.
2. Disk: the training venv (6.0 GB) lives in WSL on C:, and models and data live on D:. That fits with about 14 GB still free on C:.
3. Teacher model: only our generators and local models.
4. GGUF export: llama.cpp converter, pinned release (approved 2026-10-26).
