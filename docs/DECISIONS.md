# Decisions

One entry per decision: context, decision, consequence. Newest last.

## D-001 Project name: Partwright (2026-10-25)
The brief asked for an original name instead of the working title. "Partwright" (a maker of parts) is short and descriptive. Not trademark-checked; rename before any public release if a conflict turns up.

## D-002 Models sized to a 6 GB GPU (2026-10-25, revised same day)
The machine has an RTX 3060 Laptop with 6 GB VRAM and 16 GB RAM (`docs/HARDWARE.md`); 32B/14B-class models cannot run. Default IR and vision model is `qwen3.5:4b` (multimodal, Apache-2.0, cheap KV cache, so no model swap between IR and vision). `qwen2.5-coder:7b-instruct-q4_K_M` (already on disk) is the A/B baseline; the M1 eval decides the default and the loser stays configurable. Embeddings `qwen3-embedding:0.6b`; CI `qwen3.5:0.8b-q8_0` plus a fake LLM for unit tests. Avoid Qwen2.5-Coder-3B and Qwen2.5-VL-3B (non-commercial licence).

## D-003 Ollama as the default runtime (2026-10-25)
Ollama is installed, serves the 7B fully on GPU, and supports JSON-schema `format` on Windows (verified). vLLM needs WSL and has no headroom at 6 GB; an OpenAI-compatible adapter covers vLLM/llama.cpp server as an option behind the same `LLM` interface.

## D-004 Research via in-session sub-agents (2026-10-25)
M0 research (reference and technical) runs as parallel background sub-agents whose results feed the parity checklist and plan in this session. Build agents (M1+) work on separate git branches/worktrees per `docs/PLAN.md`.

## D-005 Licence: Apache-2.0 (2026-10-25)
Dependency check in `docs/research/SUMMARY.md`. OCCT and planegcs (LGPL) are used only as separately installed wheels with a NOTICE entry. Excluded: PyMuPDF (AGPL), marker, python-solvespace, BOLTS, FreeCAD Fasteners WB, CADAM code, Neo4j server. Non-commercial datasets (Fusion 360 Gallery, Text2CAD, CAD-Recode) are eval-only; published weights train on our procedural corpus and permissive data.

## D-006 Python 3.12, build123d only (2026-10-25)
`planegcs` (sketch constraint solver) ships cp312+ wheels only. build123d 0.13.0 on OCP 8.0.1 is the single CAD library; CadQuery 2.8 pins OCP 7.9 and breaks when co-installed (verified), so CadQuery is not a dependency. The kernel sits behind `services/geometry`'s interface, so a CadQuery backend could still be added in its own environment.

## D-007 Feature tree: IR is the source of truth; FreeCAD `.FCStd` as the native history format (2026-10-25)
STEP carries no feature history. Every model ships as IR JSON + generated build123d script + STEP/STL/GLB, and the IR is replayed into a FreeCAD `.FCStd` (PartDesign bodies, constrained sketches, named features, assembly joints) by an optional FreeCAD 1.1 subprocess. This is the open counterpart of the reference product's native Onshape output. Onshape (proprietary SaaS) is an optional adapter tested only against a recorded mock, never on the default path.

## D-008 Local-first stack without Redis (2026-10-25)
Jobs: in-process asyncio dispatcher with a SQLite job table and warm subprocess CAD workers with timeouts; one GPU job at a time. Celery has no Windows support, RQ needs fork, arq is maintenance-only. Progress streams over SSE. One SQLite file per project holds documents, chunks, FTS5, `sqlite-vec` vectors and the property graph (networkx in memory for traversal). Kùzu is archived. Postgres-readiness means SQLAlchemy Core with no SQLite-only SQL outside the vector/FTS module.

## D-009 Business and proprietary rows are scoped, not dropped (2026-10-25)
Checklist rows that are business features (quotas, community), proprietary formats (CATIA/NX/SolidWorks/Creo, Onshape) or the reference's own stated vision (supplier catalogs, differentiable workflow) are built in the smallest form that passes their acceptance test (e.g. STEP AP242 for proprietary CAD, mock-tested Onshape adapter) and any gap is listed in `docs/PARITY_REPORT.md`.

## D-010 M1 agent loop shape (2026-10-25)
One schema-constrained call emits the whole `Design`; staged emission (params → sketches → features) is added only if the M1 eval shows the single call failing on structure. A separate small call extracts checkable requirements (extent, hole count/diameter, hole spacing, wall) from the request; the loop checks the built model against them and against B-rep validity, and every failure is fed back as a repair message. Refinement answers either parameter updates or a full new design, so a pure parameter change cannot drift the rest of the model.

## D-011 Holes are recognised from the B-rep, not trusted from the IR (2026-10-25)
Spec checks read holes from the built solid: concave cylindrical faces grouped by axis and radius whose angular span adds up to 360°. This catches holes that miss the part, are blind by accident, or were never cut, and does not count slot ends or internal fillets.

## D-012 Default model confirmed: qwen3.5:4b (2026-10-25)
M1 eval: 4B fully passes 4/10 cases vs 3/10 for the 7B coder, with 21 vs 27 repairs and 145 s vs 172 s median; both pass 22/35 checks. The 4B stays default; the 7B stays configurable.

## D-013 No planning step; keep standards data, normalisation and strict hole checks (2026-10-25)
Ablation on the M1 set with `qwen3.5:4b`: a free-text planning call before IR emission scored 1/10 cases fully correct (8/35 checks); the same build without it scored 6/10 (24/35 checks, median 84 s), up from the M1 baseline of 4/10 (22/35, 145 s). The plan step was deleted. Kept: EN 1092-1 / NEMA / extrusion reference data, linking literals to unused parameters (unused ones stay errors), unused-sketch errors, holes that miss or break the edge failing with the feature named. Results in `evals/results/m1-20261025-223518` (with plan) and `m1-20261025-225624-noplan`.

## D-014 Grounding: facts become checks, citations by fact id (2026-10-25)
Retrieved facts are listed in the prompt with their ids; the model cites a fact by putting its id in a parameter's provenance, and the agent swaps in the fact's document provenance (ref + quote). Checkable facts (hole callouts, toleranced bores, size chains) become requirement checks, so the spec is enforced by geometry, not trusted from the model. Project rules reach the geometry service per process. The agent depends on `partwright_context` only for its data types; retrieval and recording happen at the edge (CLI, later the API).

## D-015 Unused parameters are dropped; repairs are fresh prompts (2026-10-25)
Failing on unused parameters made the 4B churn (it adds parameters for rule limits); requirement checks already catch a forgotten dimension, so unused parameters are removed before validation. Repairs re-send the original prompt plus a user message quoting the previous design and its problems, because the 4B repeated its last assistant turn verbatim in a growing chat even at temperature 0.5 (sampling itself was verified to vary). An exact repeat raises the temperature to 0.9.

## D-016 Rules have no scope yet (2026-10-25)
"Hole-to-edge ≥ k x D" applies to every hole, including large bores where it cannot hold (a centred Ø40 bore on an 80 mm plate). The M2 demo spec was changed to a Ø20 bore. A `scope` on `Rule` (e.g. fastener holes up to a diameter) is an IR change planned with the M3 API work.

## D-017 IR v2 P0 (2026-10-26)
Implemented as proposed in `docs/IR_V2.md`: plane references (base, datum, or a face of an earlier feature), selectors, path sketches, extrude extents with intersect and taper, revolve axis offset, semantic holes and patterns, part process. Face planes keep the base-plane coordinates of their axis and an outward offset, so the model learns one coordinate convention; cuts on a face go into the material and adds go outward automatically. Feature tools are kept by id so faces can be referenced and patterns can replay them. Regions are resolved by geometric match with the tool body. v1 designs upgrade on load (the upgrade is idempotent and always applied), and every v1 fixture rebuilds unchanged.

## D-018 Fasteners as designations (2026-10-26)
`fastener` takes `M<d>` or `M<d>x<pitch>` for M2–M30. Clearance follows ISO 273 by fit, tap drill is nominal minus pitch (ISO 261 coarse pitch by default), counterbore seats follow DIN 974-1 style head-plus-clearance, countersinks follow the ISO 10642 head diameter (2.24 d). The model wrote fine-pitch hydraulic port threads (M18x1.5, M30x1.5) as soon as v2 allowed them; a closed `M\d+` pattern rejected realistic designs, so the field is validated by parsing rather than by schema pattern.

## D-019 Single-call emission stays; staged emission deleted (2026-10-26)
A/B on IR v2 with qwen3.5:4b, same code: drafting parameters first and then the design scored 2/10 fully correct and 9/35 checks on the M1 set against 4/10 and 16/35 for one call, and was slower on the challenge set. As with the planning step (D-013), a constrained first answer that the second must follow passes its mistakes along. The switch and its prompt were removed.

## D-020 IR v2 kept although the M1 gate regressed (2026-10-26)
v2 is required for completeness (faces, datums, semantic holes) and improves the grounded set (3/10, 23/45 checks vs 2/10, 15/45), but the M1 set fell from 21/35 to 16/35 checks and generation is about twice as slow. v1 cannot express the challenge parts at all, so reverting is not an option; recovering the M1 score on v2 is the next task, before further IR growth. Results: `docs/agents/ir-v2.md`.


## D-021 Fine-tuning stays local (2026-10-26)
Training runs on the laptop only (RTX 3060 6 GB, WSL2, Unsloth bf16 LoRA), so the model we tune is Qwen3.5-0.8B; the 4B needs about 10 GB. Data comes only from our generators, kernel and local models. Ollama on Windows cannot import Qwen3.5 safetensors (it needs its MLX runtime), so the merged model is converted with llama.cpp's `convert_hf_to_gguf.py` (release b11898, pinned) to q8_0 and imported as a GGUF with the base model's renderer, parser and sampling parameters. Plan: `docs/FINE_TUNING_PLAN.md`; runs: `docs/agents/training.md`.

## D-022 Answers are written required-keys-first (2026-10-26)
Ollama's schema grammar emits all required keys of an object before any optional one. Our worked examples and the first training targets wrote some optional keys early (a sketch's `plane` before `entities`, a part's `material` and `process` before `sketches`), and under constrained decoding the model can never produce them there: profiles and turned parts silently fell back to the XY plane. A tuned 0.8B scored 24 of 27 held-out cases on the first try without the grammar and 16/40 with it. `answer_json` now writes every design we show or train on in grammar order; all earlier eval numbers with the examples were measured under this bug.

## D-023 The request overrides conflicting project facts (2026-10-26)
A request in a project whose documents say otherwise ("100 x 60 x 5" against a spec sheet's 120 x 80 x 6) produced both sets of numbers as hard checks, so no answer could pass. When the request states an extent or a counted hole group that differs from a fact of the same kind, the fact's check is dropped, the fact is left out of the prompt, and the requirements step names what was overridden. Facts the request does not contradict (a bore it does not mention) still apply. Design rules are unchanged: a request that breaks a rule (holes 8 mm from the edge where 1.5 x D needs 8.25) still fails the rule.

## D-024 The local 0.8B fine-tuning route stops after S1 (2026-10-26)
The stop rule set before S1 required the tuned model to beat the prompted qwen3.5:4b on M1 and on the grounded set. S1 scored 3/10 and 10/35 checks on M1 against the 4B's 4/10 and 15/35; on the grounded set it tied on fully passing cases (1/10) with more checks (24/45 against 14/45) and was about nine times faster. The route stops as the rule says. The pipeline stays (generators, verification, local paraphrasing, training and GGUF export are reusable), and the reference run (Sonnet 5.5: 10/10 on M1, 2/2 on the challenge set) shows the IR and checks are sufficient, so the gap is model capability. Next work goes to the prompted local model and to the agent bugs the runs exposed.

## D-025 The QLoRA-tuned 4B stays a comparison model (2026-10-27)
S1 data on Qwen3.5-4B with QLoRA (local, 8 h, exported as Q4_K_M like the base) beat the prompted qwen3.5:4b on the grounded set (grounded mode 4/10 and 25/45 against 1/10 and 14/45; prompt mode 5/10 and 35/45 against 4/10 and 20/45) and was about twice as fast, but scored 4/10 and 13/35 on M1 against 5/10 and 16/35. The stop rule needs both gates, so the default stays the prompted 4B and `partwright-ir:4b-s1` is kept in `config.yaml` for comparison. Its M1 failures fit requests to our generator families (hole sizes snapped to clearance tables, patterns read as edge margins, quotes not in the prompt), so the next data work is breadth outside those families, not more of the same.

## D-026 Repeated answers are re-sampled; prompt quotes must be in the request (2026-10-27)
The tuned 4B returned byte-identical answers on every repair: the repair prompt quotes the previous answer, and a sharply tuned model copies it back even at temperature 0.9. When an answer repeats any earlier one in the run, the agent now asks again once with the problems listed and the answer left out (`resample_message`). A parameter whose provenance is `prompt` must quote words that appear in the request (case, whitespace and the multiplication sign ignored); otherwise it is a repair problem, because an invented quote is a false provenance claim. Refines are not checked, since their quotes come from the original request.

## D-027 The tuned 4B is the default model (2026-10-27)
With the agent fixes (D-026), `partwright-ir:4b-s1` beat the prompted `qwen3.5:4b` on every gate in three runs each: M1 5/10 against 4/10, grounded mode 33/45 checks and all parts built against 25/45 and 7/10 (`docs/agents/training.md`). That meets the S1 stop rule, so it replaces `qwen3.5:4b` as `llm.default`. It is built locally and not published, so a fresh clone must build it (rebuild steps in `docs/agents/training.md`) or run with `--model qwen3.5:4b`, which stays configured. The export keeps the text layers only, so it has no vision projector: sketch and vision steps, when they land, use `qwen3.5:4b`. This supersedes D-012's choice of default and D-025.

## D-028 Gate protocol for S2: one run per model in the same session, and a dev set for checkpoints (2026-10-27)
Within a session, repeated gate runs give the same scores (three runs each on 2026-10-27), while results drift between days. Each S2 gate is therefore run once for the candidate and once for the current default, in the same session, and the stop rule is unchanged: the candidate must beat the default on M1 and on the grounded set. A 20-case dev set (`evals/cases/dev.yaml`) picks the best saved checkpoint, so M1 and grounded are only used as gates. Its parts are new, chosen to test what S2 adds: stated diameters, centre-spacing wording, off-centre outlines, neighbouring standard sizes and spec-sheet layout. It joins the training leak guard.

## D-029 S2 data: what the generators state, what they leave out, and how carried values are labelled (2026-10-27)
Holes are asked for by M-size, by plain diameter or both, and patterns by margin, centre spacing, square, PCD or rows and columns; the target keeps whatever the request states, so a stated 8.5 mm hole stays 8.5 mm instead of becoming M8. Standard parts use the agent's own EN 1092-1, NEMA and extrusion tables, cite them as `standard`, and leave out the sizes the eval sets use (DN50, NEMA 17 and 23, the 20 series); training prompts now include the same reference lines inference adds. EN 1092-1 flanges break the default 1.5 x D hole-edge rule by design, so they are exempt from that rule in verification and never shown with a project rules block. In edit samples, values carried over from the previous design are marked `user_edit` (as parameter edits already are), and only the changed value quotes the request, so carried values never claim words the request does not contain.

## D-030 How a parity row closes: a scripted demo run live, plus the same demo as an offline test (2026-10-29)
Each row gets one demo function in `evals/src/partwright_evals/parity_<area>.py` that performs the row's acceptance test against the real components (geometry worker, context store, agent loop, HTTP app) and returns the measured numbers. `partwright-parity` runs the demos with the configured model and writes `evals/results/parity-<stamp>/` (per-row artifacts, `evidence.json`, `PARITY.md`); that run is the recorded demo. The same demos run in CI with a scripted fake model (`evals/tests/test_parity_*.py`), so the plumbing is tested offline and the live run decides the rows that depend on the model. Web rows are Playwright specs that save screenshots and the same evidence shape. A row is marked done only when both pass; a live failure keeps it in progress with the measured numbers.

## D-031 Aircraft from sizing tools: airfoil sections and lofts in the IR, and a deterministic adapter (2026-10-29)
The IR gains `airfoil_section` (NACA 4-digit, chord, leading edge in the section plane, twist about the leading edge, nose-up positive) and `loft` (ordered section ids, optionally ruled). Both are additive: the compiler adds the NACA generator to a model only when the design uses sections, so existing designs compile byte-identically (golden test). Sizing-tool output enters through a `SizingAdapter` protocol in services/context; the reference `XmlSizing` adapter records each value's XML element as provenance and `aircraft_design` turns the spec into IR without a model, so the model still never emits geometry. Sections are verified by cutting the built solid at each station and fitting the NACA outline, with deviation in % chord.

## D-032 Images go to a separate vision model (2026-10-29)
The default `partwright-ir:4b-s1` has no vision projector (D-027), so `llm.vision` (default `qwen3.5:4b`) takes any design or refine call that carries images, including its repairs; requirement extraction stays on the text model. A short image instruction is appended only when images are present, so text-only prompts, and the training data built from them, are unchanged; values read from an image cite provenance `vision`. The visual critic (`critique`) is an explicit call to the same model over rendered views, not part of the generate loop until the live VM-10 run shows it flags missing features without rejecting correct parts.

## D-033 Assemblies in the IR: connectors and joints, placement compiled into the model (2026-10-29)
A design may carry an optional `assembly`: connectors are named frames on a part (origin and z/x axes as expressions over the design's parameters) and joints make a child connector coincide with a parent's, with an optional rotation and offset; the kind (fastened, revolute, slider) is recorded and exported. Placement is composed as build123d `Location`s in the compiled source, so the kernel is the only place transforms are computed and a parameter edit moves a part together with features that share the parameter. Pairwise interference (Boolean common volume) and a contact check per joint are errors for the repair loop; mass and CoG sum over placed parts. Mates travel in our IR bundle; STEP carries product structure and placements, since OCCT writes no AP242 kinematics. Designs without an assembly compile and hash byte-identically; the JSON schema grows by the optional property. A component edit shows the model one part and splices the answer back. Rejected: literal placement numbers (edits would not propagate), transform math duplicated in Python, part instancing (not needed yet).

## D-034 Mesh to parametric is a deterministic reconstructor in geometry, not a model task (2026-10-29)
`reconstruct_mesh` turns a watertight STL/OBJ into typed IR without a model: planar levels along Z from flat-face areas, one section per slab, circles fitted by trimmed least squares on wall vertices, equal holes grouped into polar or grid hole features when the centres fit within 0.05 mm, other outlines as counter-clockwise polygons. Tolerances scale with the noise estimated from planar faces; every parameter carries `mesh_fit` provenance. Accuracy is the Hausdorff distance between the input and the rebuilt tessellation. Scope is Z-stacked prismatic parts; blends come back sharp; arbitrary orientation and revolves are later work.

## D-035 Mission definitions size the aircraft deterministically (2026-10-29)
A `mission.yaml` (payload, endurance, max span) goes through a pure first-order sizing step in services/context: a mass and energy budget sets take-off mass and battery, wing loading sets area with span at 0.99 of the limit, the bay volume decides blended wing body or flying wing, Panknin's formula sets washout and a fin volume coefficient sets the fins. It yields an `AircraftSpec` for `aircraft_design` (D-031), so the model never emits geometry. Every value cites its mission fields and formula; configuration defaults (sweep, dihedral) cite the fields that chose the configuration. Parameter sweeps use `LocalGeometry.measure`, which rebuilds without exports, across parallel workers.

## D-036 S2 replaces S1 as the default model (2026-10-29)
`partwright-ir:4b-s2` (QLoRA on Qwen3.5-4B, S2 data per D-029) beat `partwright-ir:4b-s1` in one same-session run each (D-028): dev 14/20 vs 8/20 (70/95 vs 44/95 checks), M1 6/10 vs 5/10 (22/35 vs 16/35), grounded 5/10 vs 4/10 (38/45 vs 29/45) and prompt mode 6/10 vs 5/10, at a third to a half of the median time. It becomes `llm.default`; it is built locally like S1 (`training/wsl/s2.sh`, `Modelfile.4b-s2`). Known costs: more project-rule errors survive in grounded mode (4 vs 0) and one more M1 case fails to build; both are inputs to the next data round. Only the final checkpoint was exported, so the dev set compared models rather than picking a checkpoint.

## D-037 Apps, pipelines and simulation feed the deterministic builder (2026-10-29)
Outside apps and tools post IR (`POST /projects/{id}/designs`) or sizing XML (`/sizing`, through the D-031 adapter); the server validates and builds them without the model, so example apps and pipelines are deterministic and the model still never emits geometry. Materials are one open table in `partwright_ir.materials` (density, E, yield, each with a cited source), read by geometry's mass and the API's component properties. Simulation results per named face group become `simulation.stress` findings answered by the suggestion loop; no solver ships, and the parity demo uses an analytic cantilever as a stand-in. Sensitivities are central finite differences over kernel rebuilds (the `measure` op), not autodiff. An API user is the token's name; generation limits count rows in a usage table; community publications are a table and a fork copies the version folder and records `forked_from`. Per-project access control is deferred.

## D-038 FreeCAD and PrusaSlicer as optional subprocess checks; IR to PartDesign through kernel-reported sketch frames (2026-10-29)
FreeCAD 1.1.4 (LGPL) and PrusaSlicer 2.9.6 (AGPL) are never imported; they run as subprocesses at the paths in `PARTWRIGHT_FREECAD` and `PARTWRIGHT_PRUSASLICER`, and the tests and demos that need them skip or report the row open when unset. The `.FCStd` writer emits one PartDesign Body per part (a Sketch plus Pad or Pocket per extrude and hole, labelled in IR order); sketch geometry and constraints are the derived GE-3 sets, and sketch planes come from the geometry worker running the compiled model, so the kernel stays the one place placements are computed. A `Parameters` spreadsheet drives constraint values, lengths and offsets through expressions. Unmapped constructs (revolve, pattern, fillet, chamfer, shell, loft, assemblies) raise `UnsupportedExportError`. Rejected: attaching sketches to FreeCAD faces, whose frames and topological names differ from the IR's.

## D-039 DFM and assembly checks for S3 parts: corner-aware wall rays, keyed bores, one contact tolerance, gear-mesh backlash (2026-10-29)
The wall probe casts rays only up to the rule's limit through one `IntCurvesFace_ShapeIntersector` per part (a 40-tooth gear: 75 s to 1.5 s, same results), and ignores an exit through a neighbouring face turned more than 45° from facing the start face, since that ray crosses the corner the two faces share (a keyway edge read as a 0.5-0.8 mm wall), not a wall. A concave cylinder with one face over at least three quarters of a turn is a bore (keyed or flatted) and is measured as a hole. Contact and overlap share one length tolerance of 1 µm: an interference counts only when the common solid is thicker than that on average (2V/A), so Boolean and spline-fit noise along a touching flank no longer reads as interference while any real overlap does. A revolute joint between two spur gears allows the flank gap of its backlash, (b1 + b2)/4 · cos(pressure angle), so zero and nonzero backlash both pass. `shell_with_lid` sets its screws at least 1.5 clearance diameters in from the outer edge, stops the lid's lip square short of each boss, and widens the default boss to 3 pilot diameters where 2.5 × the screw size is smaller (M5, M8 and up); designs with thinner walls than 3 × clearance − boss diameter, or with those screws, compile to the corrected geometry (bug fix). Rejected: raising the wall or volume thresholds, which would hide real defects on ordinary parts.

## D-040 Midnight, electric blue and orange brand palette with a grid-and-globe backdrop (2026-10-30)
At the user's request the dark theme is midnight `#02070A` with electric blue `#0297DE` as the accent (controls, focus, selection, viewer grid) and orange `#FC734D` as a second accent used sparingly: brand mark, page eyebrow, the agent's running step, the caret, and the blue-to-orange progress line. Pages sit on a fixed dot lattice over a 96 px grid that fades out from the top, with a blue glow top left and an orange one bottom right; the viewport keeps only the glows, since the 3D grid already gives it structure. Home shows a slowly turning dot globe (2D canvas over a Fibonacci lattice, static under reduced motion). Status colours moved away from orange: warn is yellow `#FFC94A`, fail is pink-red `#FF4D6D`. The light theme is a full set in the same hues, darkened for contrast. This replaces UI_DIRECTION §1.7's "one accent, no gradients or glow"; colour literals still live only in `tokens.css`.

## D-041 Plain UI until the new design reference lands (2026-10-30)
At the user's request every stylesheet, the IBM Plex fonts, the theme colours and the dot globe are removed (supersedes D-040 and UI_DIRECTION §4), so the app renders with browser defaults while the next visual design is taken from a community Figma UI kit. What stays is only what the app needs to work, in `styles/plain.css` and `styles/tokens.css`: the 3D canvas's height and the free frame over it (the camera centres the part in that frame), visually hidden labels for screen readers, finding callouts that open on hover, focus or selection, graph fullscreen, and neutral 3D scene colours (part grey, black edges, red/green/blue axes). Markup, behaviour, i18n and accessibility are unchanged. The three e2e tests that assert the old layout (full-bleed canvas, mobile bottom sheet, parenthesised reference dimensions) are `fixme` until the new layout is in.

## D-042 Sci-fi UI Kit design: an instrument, not a dashboard (2026-10-30)
The web app follows the user's chosen Figma community kit, "Sci-fi UI Kit (Free)" (supersedes D-040 and D-041; spec of what was read in `docs/design/figma-kit-spec.md`, concept in `docs/design/kit-mockups/`). Tokens are the kit's: neutral greys on black, Primary red for accent and selection, its status ramps, square corners with 45° cuts at top-right and bottom-left on transient surfaces (menus, popovers, sheets), its Primary (white, notched), Secondary (outline) and Transparent buttons with uppercase Exo 2 labels, and its 4/8 spacing. Body type is Exo 2; display type is the kit's Nippo with Tektur as the bundled fallback, since Nippo's ITF Free Font License is not an open-source licence and its files would be redistributed by this repo. Layout: no boxed panels, sidebars or navbars. Every screen sits in a measuring frame (corner brackets, tick rails); Home is one question and prompt line over a horizon (the kit cover's planet), with parts as borderless specimens; the workspace keeps the part centred in the free frame and puts structure, parameters, checks, the agent and versions on the frame's edges as text, scales and rulers. Parameters are tick scales with a red needle; versions are a ruler; the command line is the kit's single-stroke rule. Thumbnails render with a transparent background so parts sit on the backdrop. Not taken from the file (the Figma MCP quota ran out after Buttons): fields, toggles, toasts and navigation components, which follow the extracted language instead.
